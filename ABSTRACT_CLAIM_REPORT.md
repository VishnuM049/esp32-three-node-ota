# Submitted fleet abstract vs demonstrated implementation

Source: `../01_secure_ota_updates_abstract.pdf` (three-ESP32 **"Secure OTA Updates for an IoT Device Fleet"** generated by `../refine_01.py`). This is **not** the older single-ESP32 abstract in `create_all_abstracts.py`. Status: 2026-10-28, after `NOISE_RUNTIME_TEST.md`. Distinguish code paths, hardware observation, and untested claims.

| Submitted claim | Evidence / honest status |
|---|---|
| Laptop → controller → two edges, signed Ed25519 firmware, no controller re-signing | **Demonstrated**: all three updated and reported valid; two one-shot encrypted edge v6→v7 OTAs and controller v7→v8 OTA. Controller forwards the original 109-byte signed manifest; each edge independently verifies it before `Update.end(false)`. Controller does not hold the signing private key. |
| Authenticated encrypted controller→edge links using Noise-style X25519 and ChaCha20-Poly1305 | **Demonstrated link operation**: pinned `Noise_KK_25519_ChaChaPoly_SHA256`, distinct provisioned device identities, authenticated registration/status and successful signed OTA to both edges. Native KK vectors/negative tests passed; real-device replay/tamper/wrong-key negatives and on-air capture remain **untested**. **Mac→controller is plaintext on the same AP**, so no end-to-end confidentiality or secrecy of firmware from a passive observer of *the whole AP* can be claimed. The PDF scopes encryption to the **controller→edge links**; state that scope aloud. |
| Reject unsigned, wrong-key/signature, tampered, wrong-role, or older-version image | **Hardware demonstrated on earlier secure firmware** (`SECURE_OTA.md`, `ROLLBACK_TEST.md`), with unchanged destination-side signed manifest/hash/version checks present in the Noise firmware. Not all rejection cases were rerun on the final Noise firmware; one plaintext `GET /update` to each edge's port 8080 received no HTTP response and versions stayed valid. Software `> FW_VERSION` check is **not** eFuse/physical anti-rollback. |
| First-boot self-test and automatic rollback to previous working firmware | **Controller hardware demonstrated**: deliberately failing signed v6 rolled back to healthy v5 (`ROLLBACK_TEST.md`); later controller v8 and both edge v7 first boots became valid. The edge firmware has a registration-gated first-boot rollback path, but **edge failure-driven rollback has not been tested**. Do not present it as proven on every node. |
| On first boot, *re-verify its own signature* | **Not implemented as literally written**: signed manifest and full SHA-256 are verified **before activation**. At first boot, code checks crypto/identity, network readiness and authenticated edge registration before confirmation; it does not reread the running image and re-verify its Ed25519 signature. |
| Browser-based **web log** shows each node's version and result | **Mac-local read-only log implemented** (`WEB_LOG.md`, `web_log/`): parses controller `/status`, displays three nodes, persists timestamped future state changes, and records one-shot sender acceptance/confirmation events. Offline endpoint and parser tests passed. **Not yet live-tested with all three boards powered**; it cannot retroactively show attack attempts that occurred before logging started. It is not a tamper-proof device audit log. |
| ESP32 polls/downloads from update server | **Not claimed in the submitted three-node PDF**. It says the signed image is served to the controller over Wi-Fi and the demonstration *pushes* updates. Current laptop HTTP POST to the controller and streamed relay to edges match that architecture; no separate pull scheduler is required to satisfy this PDF. |
| Automatic reconnection after controller reboot | Not a PDF promise, but **not demonstrated**: edges required manual unplug/replug after controller v8 reboot before simultaneous authenticated status returned. Avoid claiming unattended recovery. |

**Bottom line:** The **controller→edge encryption claim is covered for the named hop**, and the central signed-OTA demonstration is real. The *entire abstract* is **not fulfilled literally** yet: first-boot self-signature recheck and hardware-demonstrated edge failure rollback remain gaps; the new browser log still needs a live three-board run. Desktop and device negative-test coverage for the final encrypted firmware is incomplete. Neither a browser log nor more screenshots would by itself close those security/test gaps.
